## The problem

A catalog with a cart and orders has a dozen entities (categories, products, countries,
states, cities, users, orders) and all of them need the same things: paginated listing,
search, create, edit, delete. Writing that code thirteen times is the fastest way to end up
with thirteen endpoints behaving thirteen different ways.

Then there is the other half: confirming an order is not inserting a row. It has to validate
stock, create the detail lines, decrement inventory and empty the cart, all or nothing.

## Architecture decisions

### Generics per layer, not copy and paste

The backend follows an explicit chain: **Controller → Unit of Work → Repository → DbContext**,
with a generic implementation at each level and subclasses only where extra behaviour is
actually needed.

`GenericController<T>` exposes `GET /full`, `GET`, `GET /totalPages`, `GET /{id}`, `POST`,
`PUT` and `DELETE /{id}`. Concrete controllers inherit and **override only what differs**.
`GenericRepository<T>` and `GenericUnitOfWork<T>` provide CRUD with pagination, and
`QueryableExtensions.Paginate` centralises the `Skip`/`Take` every repository uses.

The Unit of Work is not ceremony: it is what lets `ProcessOrderAsync` validate stock, create
the `OrderDetail` lines, decrement `Product.Stock` and clear the cart as one coherent
operation.

### Errors are data

Every operation returns `ActionResponse<T>` with `WasSuccess`, `Message` and `Result`. An
out-of-stock product does not throw an exception someone has to remember to catch three
layers up: it returns a failed response that the controller maps to an HTTP code and the
frontend maps to a message.

The Blazor side mirrors it: `IRepository` wraps `HttpClient` and returns
`HttpResponseWrapper<T>`. The same mental contract on both sides of the wire.

### One shared project instead of duplicated DTOs

The solution is four projects: `Orders.Backend` (Web API), `Orders.Frontend` (Blazor
WebAssembly), `Orders.Shared` (entities, DTOs and enums) and `Orders.Tests` (MSTest).

Because the SPA and the API share `Orders.Shared`, a change to a DTO **breaks the build**
instead of breaking the app in production. That is the concrete payoff of running the same
language at both ends.

### Details that usually get forgotten

`IFileStorage` wraps Azure Blob Storage with a default interface method, `EditFileAsync`,
that deletes the previous blob before uploading the new one, the common oversight that fills
an account with orphaned images.

`AuthenticationProviderJWT` stores the token, parses its claims and feeds Blazor's
`AuthenticationStateProvider`, so role-based authorisation works on the client with the same
criteria as on the server.

## Outcome

Customer and administrator on the same foundation: a public catalog with pagination, text
search and category filter, a cart, order confirmation with stock validation, and order
history; plus full CRUD over catalogs and control of every order's lifecycle
(`New`, `Dispatched`, `Sent`, `Confirmed`, `Cancelled`).

All of it with JWT authentication and role-based authorisation, server-side pagination on
every list endpoint, transactional email over SMTP, and Swagger with `Bearer` support in
development.

> The Repository + Unit of Work pattern from this project is the same one applied to content
> access in this portfolio: pages never query the collection directly.
